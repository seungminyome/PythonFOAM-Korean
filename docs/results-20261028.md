`describe` 요청 두 개를 동시에 진행할 수 있습니다. 요청을 하나씩 진행할 때와 마찬가지로, 응답을 받은 요청
하나마다 솔버 벽시계 시간이 이미지 생성 시간 외에 약 0.1 s 늘었습니다. 저장 파일 2,520개는 모두 기준
실행(요청 없음)의 파일과 같았습니다. 콜백은 이제 텔레메트리 파일을 실행 중에 쓰므로, 실행이 길어져도 콜백의
메모리가 더는 늘지 않습니다. 기록해 둔 상태 24,000개를 재생했을 때 Python 힙은 31.7 MiB에서 최대 0.52 MiB로
줄었고, 파일은 이전과 바이트 단위까지 같습니다. 콜백은 `sequence` 요청의 추세 레이블도 배열에서 계산합니다.
관찰 기능은 3차원 케이스를 평면 단면으로 그리며, 직렬 실행과 rank 2개 실행에서 모두 동작합니다.

한 실행의 프레임 세 장에 수치 불안정의 징후가 있는지 묻자, 비전-언어 모델(VLM) 네 개는 시퀀스 54개 중
30\~33개를 맞혔습니다. 상수 기준선은 27개입니다. 최대 |U|의 증가와 인접 셀 사이 최대 |U| 차이의 증가를
배열에서 계산해 판정하는 규칙은 각각 33개와 38개를 맞혔습니다. 정상 종료한 실행의 시퀀스에는 모든 모델이
`stable`이라고 응답했습니다. 마지막 프레임이 중단(crash) 직전 시간 단계인 시퀀스 세 개에는 모든 모델이
`unstable`이라고 응답했는데, 이 시퀀스에서는 필드가 이미 발산해 있었습니다. 모델마다 이 밖에 0\~3개를 더
`unstable`로 판정했고, 그중 중단보다 5단계 넘게 앞서 끝나는 시퀀스는 없었습니다. 다만 이 시험 세트에서는
요청마다 적은 프레임 시점만으로도 두 부류가 구분됩니다.

상수 기준선은 모든 이미지(불안정 감지 시험에서는 모든 시퀀스)에 같은 답을 낼 때의 최고 점수입니다. 응답한
위치는 정답 셀에서 표시 영역 크기의 10 % 이내에 있으면 맞힌 것으로 셉니다. v2 이미지는 이미지 한 장에 필드
하나를 그리며, 축을 표시 영역의 퍼센트로 적고 10 %마다 격자선을 긋습니다. 응답은 기록만 하며, 모델 출력은
솔버 계산에 반영하지 않습니다.

## 요청 두 개 동시 진행

NVIDIA L40S에서 슬롯 두 개(`LLM_PARALLEL=2`)로 실행한 Gemma 4 12B 서버에, 발달한 유동에서 시작해 6,000단계
동안 50단계마다 v2 `describe` 요청을 보냈습니다. 대기 중인 요청은 최대 두 개로 두었습니다(`LLM_ASYNC_MAX_PENDING=2`).
조건은 같고 요청만 보내지 않는 기준 실행도 계산했습니다. 아래 표는
[inflight.py](evidence/2026-10-28-inflight/inflight.py)로 계산했으며, 이 실행 쌍을 250단계마다 요청을 하나씩
보낸 [10월 27일 보고서](results-20261027.md)의 실행 쌍과 비교합니다. 열 하나가 실행 한 쌍이고, 두 쌍은 서로
다른 노드에서 실행했습니다.

| | 두 개 동시 진행, 50단계마다 | 하나씩 진행, 250단계마다 |
|---|---:|---:|
| 계획한 요청 / 응답을 받은 요청 | 120 / 118 | 96 / 96 |
| 대기 중인 요청이 이미 두 개라 건너뜀 | 2 | 0 |
| 다른 요청이 대기 중일 때 보냄 | 112 | 0 |
| 기준 실행과 같은 저장 파일 | 2,520개 중 2,520개 | 2,016개 중 2,016개 |
| 단계당 벽시계 시간, 요청 없음 / 있음 | 0.06165 / 0.06363 s(+3.2 %) | 0.05794 / 0.05833 s(+0.7 %) |
| 응답을 받은 요청 하나당 추가 벽시계 시간 | 0.101 s | 0.097 s |
| 요청 단계의 콜백 시간, 최댓값(마지막 단계 제외) | 0.046 s | 0.017 s |
| 모델 시간, 최소 / 중앙값 / 최대 | 2.54 / 3.80 / 4.65 s | 4.15 / 4.73 / 5.25 s |
| 최대 속도 지점 10 % 이내(상수 기준선) | 117개 중 81개(62) | 96개 중 65개(53) |
| 최저 압력 지점 10 % 이내(상수 기준선) | 117개 중 106개(78) | 96개 중 89개(65) |

- 기준 실행도 같은 이미지를 생성했으므로, 추가 벽시계 시간은 이미지 생성 외에 요청에 드는 비용입니다. 응답을
  받은 요청 하나당 비용이 두 쌍에서 거의 같으므로, 요청이 다섯 배이면 비용도 약 다섯 배입니다.
- 응답을 받은 요청 가운데 4100단계의 요청 하나는 기록이 남지 않았습니다. 요청 기록을 저장하는 포크한 쓰기
  프로세스는 0.2 s가 지나면 멈추도록 되어 있어서, 솔버는 그보다 오래 기다리지 않습니다. 응답이 도착한
  4167단계는 0.207 s가 걸렸습니다. 그래서 이 요청의 폴더에는 `llm_result.json`이 없지만, 요청 목록에는 `ok`로
  적혀 있었습니다. 솔버는 영향을 받지 않았습니다. 이제 요청 목록은 요청마다 `record_written`을 기록하고,
  `run_periodic.py --summary-only`는 이런 요청을 나열하고 점수에서 뺍니다(채점한 요청 117개).

## 실행 중에 쓰는 텔레메트리

이전 콜백은 마지막 단계에서 `telemetry.jsonl`을 쓰기 위해, 모든 시간 단계의 상태를 실행이 끝날 때까지 메모리에
보관했습니다. 이제는 각 단계의 기록 한 줄을 그 단계에서 바로 인코딩하고, 메모리에는 첫 상태와 마지막 세 상태만
남깁니다. 인코딩한 줄은 제한 시간이 0.2 s인 포크한 쓰기 프로세스가 500줄 또는 60 s마다, 그리고 마지막
단계에서 파일에 일괄 추가합니다([콜백 근거 자료](evidence/2026-10-28-callback/README.md)).

| | 이전 | 현재 |
|---|---:|---:|
| 10월 27일에 기록한 상태 24,000개를 재생할 때의 Python 힙(`memory.py`) | 31.7 MiB | 최대 0.52 MiB(추가한 뒤 0.07 MiB) |
| 파일을 쓰는 마지막 단계(재생) | 0.699 s | 0.023 s |
| PODFoam에서 일반 단계의 콜백 시간, 중앙값 | 0.08\~0.11 ms | 0.16\~0.22 ms |
| 파일에 추가하는 단계(500단계와 1,000단계) | – | 13.7\~22.0 ms |
| `telemetry.jsonl` | | 솔버 실행 세 쌍(1,250단계; 직렬 `describe`, 직렬 `sequence`, rank 2개)과 상태 24,000개 재생에서 바이트 단위까지 같음 |

- 새 콜백을 쓴 실행의 저장 필드, 프레임, 요청 본문은 모두 이전 콜백을 쓴 실행과 같습니다.
- 실행 중에는 `telemetry.jsonl.tmp`만 있고 마지막 단계에서 이 파일의 이름을 바꾸므로, `telemetry.jsonl`은
  완전한 상태로만 생깁니다. 쓰기에 실패하면 `llm_errors.jsonl`에 한 번 보고하며, 솔버는 멈추지 않습니다.
- 각 단계의 기록 한 줄을 솔버 프로세스에서 인코딩하므로, 이제 일반 단계는 약 0.1 ms씩 더 걸립니다.

## 추세 레이블 계산

v2 `sequence` 요청에서 콜백은 이제 표시 영역 안의 프레임 배열에서 추세 레이블 세 개를 계산합니다. 규칙은
정답을 만들 때와 같습니다. 최대 속도와 최저 압력의 추세는 상대 변화 2 %를 기준으로, 최대 속도 지점의 이동
여부는 표시 영역 크기의 5 %를 기준으로 판정합니다. 계산한 레이블은 `llm_result.json`의 `computed_trends`에
기록하고, 모델이 응답했으면 `computed_trends_agreement`도 기록합니다. 100, 150, 200단계에 프레임을 둔 솔버
실행에서 레이블은 `increasing`(+2.44 %), `more_negative`(−10.9 %), `moves`(표시 영역 크기의 6.92 %)였고,
이미지 시험의 정답과 같았습니다. 이 실행들에서는 모델이 응답하지 않았으므로, `computed_trends_agreement`는
테스트 서버로만 확인했습니다. 기본 설정에서는 요청이 바이트 단위까지 그대로입니다. `LLM_SEQUENCE_PROMPT=t`는
정답의 임계값을 프롬프트에 추가하고, `tn`은 여기에 더해 시점마다 최대 |U|와 최저 p를 적습니다.

## 3차원 케이스: 평면 단면

v2 이미지를 만들 때 관찰 기능은 2차원 케이스의 `empty` 패치에서 셀마다 다각형 하나를 얻는데, 3차원 격자에는
이 패치가 없습니다. 이제 PODFoam은 OpenFOAM의 `cuttingPlane`으로 3차원 격자를 z = `LLM_SLICE_Z`에서 자르고,
관찰 기능은 잘린 셀을 각각 다각형 하나로 그립니다([3차원 근거 자료](evidence/2026-10-28-3d/README.md)).
`LLM_SLICE_Z`의 기본값은 z 범위의 가운데이며, 그 위치가 격자점이 놓인 평면이면 평면을 비켜 옮깁니다. 시험
케이스는 후향 계단 유동 케이스를 z 방향으로 셀 8개만큼 압출하고 앞뒤를 벽으로 막은 것으로(셀 164,320개),
t = 0.1 s의 2차원 상태에서 시작해 150단계를 계산했습니다.

- 단면에는 다섯 번째 층의 셀 20,540개가 있으며, 2차원 셀 하나에 하나씩 대응합니다.
- rank 2개에서도 단면의 셀은 직렬 실행과 같습니다. 셀 중심은 4.2×10⁻¹⁷ m 이내로 일치하고, 다각형 꼭짓점은
  똑같습니다. U 차이는 2.5×10⁻³ m/s 이내(가장 큰 성분 37.2 m/s), p 차이는 0.036 m²/s² 이내(가장 큰 |p|
  282 m²/s²)입니다.
- 프레임은 그 단계의 저장 필드와, 파일에 저장된 12자리까지 같습니다. 저장 파일 63개는 모두 관찰 기능을 쓰지
  않은 실행의 파일과 같고, 요청 본문은 테스트를 거친 빌더를 프레임에 적용한 결과와 같습니다.
- `LLM_SLICE_Z`가 잘못되었거나 평면이 아무 셀도 자르지 않으면 솔버가 경고를 내고, 요청은 거부됩니다. 이런
  실행도 끝까지 진행했습니다.
- 2차원 케이스의 동작은 그대로입니다. 2차원 프레임과 요청 본문은 10월 27일 MPI 시험의 것과 파일 단위로 같고,
  연결 검증도 통과합니다.

## 수치 불안정 감지 시험

중심 차분과 더 큰 시간 간격을 쓰면 계단 케이스의 실행은 중단됩니다. Δt = 3×10⁻⁵ s에서는 27단계,
4×10⁻⁵ s에서는 10단계, 2×10⁻⁵ s에서는 더 길게 실행했을 때 467단계에서 중단되었습니다. 모델 네 개에 한 실행의
v2 프레임 세 장을 보여 주고, 그 실행에 수치 불안정의 징후가 있는지 물었습니다. 프레임마다 |U|와 p 이미지가
있으며, 이미지별 색 범위를 쓰고 표시 영역은 솔버가 그리는 영역과 같습니다. 채점한 시험 세트에는 마지막
프레임이 중단 1\~10단계 전인 시퀀스 27개와, 종료 시간에 도달한 실행의 시퀀스 27개가 있습니다. 종료 시간에
도달한 실행은 풍상 차분 실행, 발달한 유동, 작은 시간 간격의 중심 차분 실행입니다([불안정 감지
근거 자료](evidence/2026-10-28-instability/README.md)).

| 판정 방법 | 맞힌 수(54개 중) | 중단 임박: `unstable` 판정(27개 중) | 정상 종료: `stable` 판정(27개 중) |
|---|---:|---:|---:|
| Gemma 4 12B | 32 | 5 | 27 |
| Gemma 4 26B-A4B | 30 | 3 | 27 |
| Gemma 4 31B | 33 | 6 | 27 |
| Qwen3.5-35B-A3B Q8_0 | 32 | 5 | 27 |
| 상수 기준선 | 27 | | |
| 규칙: 표시 영역 안의 최대 \|U\|가 20 % 넘게 증가 | 33 | 6 | 27 |
| 규칙: 인접 셀 사이 최대 \|U\| 차이가 50 % 넘게 증가 | 38 | 11 | 27 |

- 마지막 프레임이 중단 직전 단계인 시퀀스 3개에는 모든 모델이 `unstable`이라고 응답했습니다. 이 시퀀스에서는
  필드가 이미 발산했습니다(최대 |U| 84.6 m/s\~1.5×10⁴⁰ m/s). 그 밖에 모델마다 0\~3개를 더 `unstable`로
  판정했고, 그중 가장 이른 시퀀스는 중단 5단계 전에 끝났습니다.
- 모델이 `unstable`로 판정한 시퀀스에서는 모두 최대 |U|가 30.8 % 이상 증가했습니다. 이 수치 하나만 보는
  규칙도 가장 좋은 모델만큼 맞히고, 인접 셀 사이 차이를 보는 규칙은 더 많이 맞힙니다. 이 시험 세트에서 이미지는
  색 막대의 숫자 이상을 보태지 못했습니다.
- 이 시험 세트에는 결함이 있습니다. 요청마다 프레임의 시점을 적었고, 중단된 실행의 프레임은 정상 종료한 실행의
  프레임보다 시간상 서로 가깝습니다. 그래서 프레임 사이 시간만으로도 두 부류를 가를 수 있습니다(54개 중
  54개). 그럼에도 모델은 중단된 실행의 시퀀스 대부분을 `stable`로 판정했습니다.

## 한계

- 단면 이미지를 읽은 모델은 없으며, 이미지와 요청 어디에도 단면이라는 표시가 없습니다. z에 수직인 평면으로
  자른 압출 육면체 격자만 시험했고, OpenFOAM은 v2212만 썼습니다.
- 이미지로든 수치로든, 중단보다 몇 단계 넘게 앞서 경고할 수 있다는 결과는 이 보고서에 없습니다.
- 요청 세 개 이상을 동시에 진행하는 경우와, 느린 디스크에 요청 기록을 쓰는 경우는 시험하지 않았습니다.

## 향후 작업

1. 발달한 3차원 유동의 단면 이미지로 모델을 시험합니다.
2. 프레임을 같은 간격으로 두고 시점을 적지 않은 불안정 감지 시험을 합니다. 이때 콜백에서 계산한 수치
   경고(최댓값 증가, 인접 셀 사이 차이)를 모델의 응답 옆에 둡니다.
3. 요청 기록을 쓰는 데 더 긴 제한 시간을 주거나, 워커가 직접 기록을 쓰게 합니다.
4. 관찰 기능을 PythonFOAM에 기여합니다.
