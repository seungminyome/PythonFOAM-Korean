## 요청 두 개를 동시에

50걸음마다 v2 describe 요청, 기다리는 요청은 최대 둘(`LLM_ASYNC_MAX_PENDING=2`), 슬롯이 두 개인
서버(`LLM_PARALLEL=2`), 발달한 흐름에서 6,000걸음, 그리고 요청 없는 같은 실행(작업 24929296, Gemma 4 12B,
NVIDIA L40S). 250걸음마다 요청 하나를 보낸 10월 27일 실행과 비교하면([inflight.py](evidence/2026-10-28-inflight/inflight.py)):

| | 두 개 동시, 50걸음마다 | 하나씩, 250걸음마다 |
|---|---:|---:|
| 계획한 요청 / 답한 요청 | 120 / 118 | 96 / 96 |
| 기다리는 요청이 이미 둘이라 건너뜀 | 2 | 0 |
| 다른 요청을 기다리는 동안 보냄 | 112 | 0 |
| 요청 없는 실행과 같은 저장 파일 | 2,520개 중 2,520개 | 2,016개 중 2,016개 |
| 걸음당 벽시계 시간, 요청 없음 / 있음 | 0.06165 / 0.06363 s(+3.2 %) | 0.05794 / 0.05833 s(+0.7 %) |
| 답한 요청 하나당 더 든 벽시계 시간 | 0.101 s | 0.097 s |
| 요청 걸음에서 콜백이 쓴 시간, 최대(마지막 걸음 제외) | 0.046 s | 0.017 s |
| 모델 시간, 최소 / 중앙값 / 최대 | 2.54 / 3.80 / 4.65 s | 4.15 / 4.73 / 5.25 s |
| 가장 빠른 곳이 10 % 안(답 하나로 고정) | 117개 중 81개(62) | 96개 중 65개(53) |
| 가장 낮은 압력이 10 % 안(답 하나로 고정) | 117개 중 106개(78) | 96개 중 89개(65) |

- 요청 두 개가 나란히 돌았고, 기다리는 요청이 이미 둘인 걸음은 설계대로 건너뛰고 기록했습니다.
- 두 실행 모두 요청 하나에 솔버 벽시계 시간이 약 0.1 s 듭니다. 그림 그리기에 더해서이고(요청 없는 실행도
  그림을 그렸음), 그래서 요청이 다섯 배면 비용도 약 다섯 배입니다. 각각 실행 한 쌍이고, 노드는 서로 다릅니다.
- 답 하나는 기록되지 않았습니다. 4100걸음의 요청은 답을 받았지만(4167걸음), 그 기록을 쓰는 포크한 쓰기
  프로세스는 솔버가 그보다 오래 기다리지 않도록 0.2 s 뒤에 멈추고, 그 걸음은 0.207 s 걸렸습니다. 그래서
  폴더에는 `llm_result.json`이 없는데 목록에는 `ok`라고 적혔습니다. 솔버는 영향을 받지 않았습니다. 이제 목록은
  요청마다 `record_written`을 기록하고(`56646b9`), `run_periodic.py --summary-only`는 그런 요청을 나열하고
  점수에서 뺍니다(`c85c79c`).

## 상태를 쌓아 두지 않는 콜백의 텔레메트리

콜백은 `telemetry.jsonl`을 쓰려고 걸음마다의 상태를 실행이 끝날 때까지 모두 들고 있었습니다(24,000걸음에
32 MiB). 이제는 걸음이 오면 그 걸음의 줄을 바로 인코딩하고, 마감이 0.2 s인 포크한 쓰기 프로세스가 줄을
묶음으로 덧붙이며(500줄 또는 60 s마다, 그리고 마지막 걸음에서), 첫 상태와 마지막 세 상태만 남깁니다
([콜백 근거 자료](evidence/2026-10-28-callback/README.md), 작업 24929555):

| | 전 | 지금 |
|---|---:|---:|
| 10월 27일에 기록된 상태 24,000개에서 Python 힙(재생, `memory.py`) | 31.7 MiB | 최대 0.52 MiB(덧붙인 뒤 0.07 MiB) |
| 파일을 쓰는 마지막 걸음(재생) | 0.699 s | 0.023 s |
| PODFoam에서 보통 걸음의 콜백 시간, 중앙값 | 0.08~0.11 ms | 0.16~0.22 ms |
| 덧붙이는 걸음(500걸음과 1,000걸음) | – | 13.7~22.0 ms |
| `telemetry.jsonl` | | 솔버 실행 세 쌍(1,250걸음; 직렬 describe, 직렬 sequence, rank 2개)과 상태 24,000개 재생에서 바이트까지 같음 |

- 새 콜백으로 돈 실행의 저장 필드, 프레임, 요청 본문은 모두 예전 콜백으로 돈 실행과 같습니다.
- 파일은 완전하거나 아예 없습니다. 실행 중에는 `telemetry.jsonl.tmp`만 있고, 마지막 걸음에서 이름을
  바꿉니다. 실패한 쓰기는 `llm_errors.jsonl`에 한 번 알리고, 솔버는 멈추지 않습니다.
- 이제 보통 걸음마다 약 0.1 ms가 더 듭니다. 그 걸음의 줄을 솔버 프로세스에서 인코딩하기 때문입니다.

## 계산한 증감 단어

이제 v2 sequence에서 콜백은 증감 단어 세 개를, 그린 범위 안의 프레임 배열로부터 정답의 규칙(상대 변화 2 %,
자리는 범위의 5 %)으로 계산해 `llm_result.json`에 기록합니다(`computed_trends`, 그리고 모델이 답했으면
`computed_trends_agreement`). 요청은 그대로입니다. 100, 150, 200걸음에 프레임을 둔 솔버 실행에서는
`increasing`(+2.44 %), `more_negative`(−10.9 %), `moves`(범위의 6.92 %)였고, 그림 시험의 정답과 같았습니다.
`LLM_SEQUENCE_PROMPT=t`나 `tn`은 10월 27일의 형태, 곧 기준을 적은 것이나 기준과 시각마다의 극값을 적은 것을
보냅니다. 기본값은 10월 22일 요청을 바이트까지 그대로 보냅니다. 이 실행들에서는 모델이 답하지 않았으므로,
일치 항목은 시험 서버로만 확인했습니다.

## 3차원 경우: 평면 단면

v2 그림에는 2차원 경우의 empty 패치에서 얻는, 칸마다 다각형 하나가 필요했습니다. 이제 3차원 격자는
PODFoam이 OpenFOAM의 `cuttingPlane`으로 z = `LLM_SLICE_Z`에서 자르고(기본은 z 범위의 가운데, 격자점이 놓인
평면이면 비켜 옮김), 관찰 기능은 잘린 칸을 저마다 다각형 하나로 그립니다([3차원 근거 자료](evidence/2026-10-28-3d/README.md)).
시험 경우는 계단 경우를 z 방향으로 칸 8개만큼 늘이고 앞뒤를 벽으로 막은 것이며(칸 164,320개), t = 0.1 s의
2차원 상태에서 시작해 150걸음을 돌았습니다(작업 24929629):

- 단면에는 칸 20,540개가 있습니다. 2차원 칸마다 하나씩이고, 다섯 번째 층에 있습니다.
- rank 2개에서도 직렬 실행과 같은 칸입니다. 칸 중심은 4.2×10⁻¹⁷ m까지 같고, 다각형 꼭짓점은 똑같으며, U는
  2.5×10⁻³ m/s(37.2 중), p는 0.036 m²/s²(282 중) 안입니다.
- 프레임은 그 걸음의 저장 필드와 저장된 12자리까지 같습니다. 저장 파일 63개는 모두 관찰 기능 없는 실행과
  같습니다. 요청 본문은 시험한 빌더를 프레임에 적용한 결과와 같습니다.
- 잘못된 `LLM_SLICE_Z`나 아무 칸도 자르지 않는 평면이면 솔버가 경고하고 요청을 거부합니다. 실행은 끝까지
  돌았습니다.
- 2차원 경우는 그대로입니다. 2차원 프레임과 요청 본문은 10월 27일 MPI 시험의 것과 파일마다 같고, 연결
  검증도 통과합니다.

아직 단면 그림을 읽은 모델은 없고, 그림에도 요청에도 단면이라는 말은 없습니다. z에 수직인 평면으로 자른,
늘여 만든 육면체 격자만, 그리고 OpenFOAM v2212로만 시험했습니다.

## 모델이 불안정해지는 실행을 알아볼 수 있는가?

중심 차분과 더 큰 시간 간격으로 돌린 계단 경우는 몇 걸음 뒤 중단됩니다(crash). `central-dt3e-5`는 27걸음,
`central-dt4e-5`는 10걸음, `central-dt2e-5`는 이어서 돌렸을 때 467걸음에서입니다. 모델 네 개에게 v2 프레임
세 장(|U|와 p, 저마다 제 색 범위, 솔버의 창)을 보여 주고, 실행에 수치 불안정의 징후가 있는지 물었습니다.
마지막 프레임이 중단 1~10걸음 전인 세 장 묶음 27개, 그리고 끝까지 돈 실행(풍상 실행, 발달한 흐름, 작은 시간
간격의 중심 차분 실행)에서 27개입니다([불안정 근거 자료](evidence/2026-10-28-instability/README.md), 작업
24929533과 24929534, NVIDIA L40S):

| 답한 것 | 54개 중 맞힘 | 중단이 다가옴, `unstable`이라 함(27개 중) | 끝까지 돈 실행, `stable`이라 함(27개 중) |
|---|---:|---:|---:|
| Gemma 4 12B | 32 | 5 | 27 |
| Gemma 4 26B-A4B | 30 | 3 | 27 |
| Gemma 4 31B | 33 | 6 | 27 |
| Qwen3.5-35B-A3B Q8_0 | 32 | 5 | 27 |
| 답 하나로 고정 | 27 | | |
| 규칙: 창 안의 최고 \|U\|가 20 % 넘게 커짐 | 33 | 6 | 27 |
| 규칙: 이웃한 칸 사이의 가장 큰 \|U\| 차이가 50 % 넘게 커짐 | 38 | 11 | 27 |

- 마지막 프레임이 중단 바로 전 걸음인 묶음 3개에서는 모든 모델이 `unstable`이라고 했습니다. 그때는 필드가
  이미 발산했습니다(가장 큰 |U| 84.6 m/s~1.5×10⁴⁰ m/s). 그 밖에는 0~3개가 더 있었고, 가장 이른 것은 그
  중단 5걸음 전입니다. 끝까지 돈 실행을 `unstable`이라 한 모델은 없습니다.
- 모델이 `unstable`이라 한 묶음은 모두 최고 |U|가 30.8 % 이상 커졌습니다. 그 숫자 하나만 보는 규칙이 가장
  나은 모델만큼 맞히고, 이웃한 칸 사이 차이를 보는 규칙은 더 잘 맞힙니다. 이 묶음에서 그림은 색 막대의 숫자
  이상을 보태지 않았습니다.
- 이 묶음에는 결함이 있습니다. 요청마다 프레임의 시각을 적는데, 중단된 실행의 프레임은 끝까지 돈 실행의
  것보다 서로 가까워서, 프레임 사이 시간만으로 두 부류가 갈립니다(54개 중 54개). 그래도 부정적인 결과는
  그대로입니다. 모델은 중단된 실행 대부분에 `stable`이라고 했기 때문입니다.

## 이 결과가 보여 주는 것과 보여 주지 않는 것

- 비동기 경로는 요청 두 개를 동시에 진행하면서도 솔버를 요청 하나당 약 0.1 s보다 더 늦추지 않고, 저장
  파일은 모두 그대로입니다.
- 콜백의 메모리는 더는 실행과 함께 늘지 않습니다. 텔레메트리 파일은 전과 바이트까지 같습니다.
- 증감 단어는 콜백에서 정확히 계산해 모델의 단어 옆에 기록할 수 있습니다.
- 관찰 기능은 3차원 경우의 v2 그림을 평면 단면으로 그리고, rank 2개에서도 그립니다.
- 시험한 모델은 그림에서 다가오는 중단을 미리 알리지 못합니다. 이미 발산한 실행을 알아볼 뿐입니다.

보여 주지 않는 것:

- 단면 그림을 읽는 모델; 다른 3차원 격자나 다른 평면 방향.
- 실시간 모델의 답 옆에 놓인 계산한 증감 단어.
- 그림이나 숫자로 몇 걸음보다 일찍 중단을 알리는 것; 시각을 적는 결함이 없는 묶음.
- 동시에 진행하는 요청 셋 이상; 느린 디스크에서의 기록 쓰기 프로세스(기록 118개 중 1개를 잃음).
- 답의 쓰임. 모델에서 나온 것은 아무것도 솔버로 돌아가지 않습니다.
