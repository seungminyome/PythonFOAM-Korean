# 10월 30일: OpenFOAM 버전, 원본 PODFoam, 잘못된 설정 시험

MedicineBow 클러스터, 2026-10-30 · NVIDIA A30, NVIDIA L40S와 CPU 노드 · llama.cpp b11429, 커밋 `d812350` · Slurm 작업과 코드: [기록](#기록)

[README](../README.md) · 근거 자료: [버전과 원본 비교](evidence/2026-10-30-versions/README.md), [잘못된 설정 시험](evidence/2026-10-30-wrong-setup/README.md) · 이후: [11월 2일](results-20261102.md), [11월 3일](results-20261103.md) · [영문](https://github.com/seungminyome/PythonFOAM/blob/main/docs/results-20261030.md)

요약: 관찰 기능은 OpenFOAM v2012, v2106, v2212, 8에서 빌드되고 점검을 통과합니다.
원본 PODFoam은 SVD 구간의 첫 스냅샷을 덮어써서 POD 모드가 이 포크와 다릅니다. OpenFOAM 8에서는
두 코드의 유동장이 같습니다. 첫 잘못된 설정 시험에서 Gemma 4 31B가 간단한 규칙을 앞섰지만, 그 우위는 실행 두 개에서
나왔습니다. [11월 3일 보고서](results-20261103.md)가 이 결과를 다시 시험합니다.

관찰 기능을 넣은 PODFoam은 OpenFOAM v2012, v2106, v2212, 8에서 빌드되고 연결 검증을 통과합니다.
v2012, v2106, v2212에서 관찰 기능의 프레임은 바이트까지 같습니다.

OpenFOAM 8은 100단계에서 U가 v2212와 최대 3.18 m/s 다릅니다. 외부 보정이 하나일 때 케이스의
`relaxationFactors`를 OpenFOAM 8은 적용하고 openfoam.com은 적용하지 않기 때문입니다
([11월 2일](results-20261102.md#openfoam-8이-v2212와-다른-까닭)).

OpenFOAM 8에서 원본 PODFoam과 비교하면 U, p, phi는 바이트까지 같고 POD 모드는 다릅니다.
`6fde869`의 원본 코드는 SVD 구간의 첫 스냅샷을 C++ 버퍼의 뷰로 들고 있었고, 다음 스냅샷이 그
버퍼를 덮어썼습니다.
Python에서 이 덮어쓰기를 재현하면 모든 POD 모드가 원본과 같습니다.

openfoam.com에서는 PR 트리가 그 버전의 `pimpleFoam`처럼 p를 풀므로 U와 p가 원본과 다릅니다.
첫 저장 시각에서 p는 5,142 m²/s² 중 847 다릅니다. 원본의 압력 줄을 쓰고 Python에서 덮어쓰기를
재현하면 모든 POD 모드가 원본과 같고, U, p, phi는 바이트까지 같습니다.

실행의 설정이 잘못되었는지 물었을 때 Gemma 4 31B는 프레임 80개 중 67개를 맞혔습니다. 최대
|U| 규칙은 56개를 맞혔고, 31B의 우위는 실행 두 개에 기댑니다.

연결 검증은 PODFoam을 직렬로 10단계 실행해 `pimpleFoam`과 비교합니다. Python이 가진 스냅샷,
돌려준 POD 모드, U와 p를 확인합니다([검증 README](../Solver_Examples/PODFoam/validation/README.md)).
`LLM_ENABLED=0`이면 관찰 기능은 프레임과 원격 측정을 쓰지만 모델에 요청은 보내지 않습니다. 프레임은
한 시간 단계의 `U.png`, `p.png`, `fields.npz`, `readable-metadata.json`입니다.

원본 PODFoam은 `6fde869`의 [argonne-lcf/PythonFOAM](https://github.com/argonne-lcf/PythonFOAM)입니다.
PR 트리는 그 코드에 이 포크의 솔버와 관찰 기능 파일을 더하고 실험 스크립트를 뺀 것입니다. 대역
서버는 고정된 답을 주며 이미지를 읽지 않습니다. 두 프레임의 차이는 셀 전체에서 가장 큰 |ΔU|와,
각 p의 평균을 뺀 뒤 가장 큰 |Δp|입니다. 이 값은 최대 |U|와 p의 범위에 견주어 적습니다.

- **POD 모드.** `6fde869`의 제공된 모듈은 구간의 첫 스냅샷을 C++ 버퍼의 뷰로 들고 있었고, 다음
  스냅샷이 그 버퍼를 덮어썼습니다. 이 때문에 모든 스냅샷 행렬의 앞 두 열이 같았습니다. OpenFOAM 8에서
  제공된 케이스 실행의 행렬 6개 중 6개, 안정화한 실행의 30개 중 30개입니다.

  같습니다.
- **openfoam.com의 압력.** 외부 보정이 하나이면, 그곳에서 원본의 단순한 `pEqn.solve()`는 모든 보정에서

  ([11월 2일](results-20261102.md#openfoamcom의-압력-솔버)).
- PR 트리는 그 버전의 `pimpleFoam`처럼 마지막 보정의 마지막 비직교 반복에서만 `pFinal`을 씁니다.
  차이의 크기는 세 버전에서 같습니다.

**PODFoam 사용자에게 달라지는 다른 점.** 전체 목록은
[검증 README](../Solver_Examples/PODFoam/validation/README.md#podfoam에서-달라지는-점)에 있습니다.

- 모드 파일은 무차원 `zeroGradient` 필드입니다. 원본 빌드는 모드 파일을 U 성분의 복사본으로 썼습니다. 차원은
  U의 것이었고, 경계에는 U의 경계값을 그대로 둔 `calculated` 패치가 있었습니다.
- 부동소수점 트랩은 솔버에서 켜져 있고 Python 구간에서 꺼집니다. 원본 빌드에서 오버플로를 지나 계속되는
  실행이 여기서는 SIGFPE로 멈춥니다.
- 제공된 모듈의 `online_mode = False`는 짧은 시험의 `writeInterval` 3과 6에서 멈췄습니다. 아주 작은 음의
  고유값이 `np.sqrt`에서 NaN이 되고, 돌려준 POD 모드는 유한해야 하기 때문입니다.
- 원본 빌드는 같은 케이스에서 종료 코드 0으로 끝났습니다(작업 24950748과 24950749).
- `Py_FinalizeEx()`는 끝에서 실행되고 데몬이 아닌 스레드를 기다리므로, 그런 스레드를 시작한 모듈은 스레드를
  멈추기도 해야 합니다. 그런 스레드가 있는 시험 모듈은 여기서 제한 시간에 멈췄고, 원본 빌드는 종료 코드
  0으로 끝났습니다.
- `podSvdInterval`이 0보다 크면 POD 필드만 든 시간 폴더가 생길 수 있습니다. 그 폴더가 가장 최근이면
  `startFrom latestTime`은 `p`가 없어서 멈춥니다.

## 모델이 잘못된 설정을 알아볼 수 있는가?

계단 케이스를 `pimpleFoam`으로 돌린 실행의 한 상태에서 v2 이미지 두 장을 모델 네 개에 보여 주었습니다.
의도한 설정을 말로 알려 주고, 이미지가 그 설정과 맞는지 물었습니다. 어떤 종류의 실수인지는 말하지 않습니다.

세트는 요청 80개입니다. 정상 실행 다섯 개와 항목 하나를 바꾼 실행 다섯 개에서 각각 상태 8개를 골랐습니다.
모든 실행은 정상 종료했습니다([근거 자료](evidence/2026-10-30-wrong-setup/README.md)).

정상 프레임에 `consistent`, 잘못된 프레임에 `inconsistent`라고 답하면 맞은 것입니다. `cannot_tell`은 양쪽
모두 틀린 것이며, 이렇게 답한 모델은 없습니다. 규칙은 표시 영역의 최대 |U|가 주어진 32.2 m/s의 1배와 2배
사이이면 `consistent`라고 합니다.

| 실행 | 변경 | 12B | 26B-A4B | 31B | Qwen | 규칙 |
|---|---|---:|---:|---:|---:|---:|
| N1\~N5 | 없음, 프레임 40개 | 40 | 40 | 38 | 40 | 40 |
| M1 | 입구 속도 32.2 m/s 대신 3.22 m/s | 1 | 0 | 8 | 0 | 8 |
| M2 | ν = 1.56×10⁻⁵ m²/s 대신 1.56×10⁻³ m²/s | 0 | 2 | 8 | 5 | 0 |
| M3 | `lowerWall`과 `upperWall`이 `noSlip` 대신 `slip` | 0 | 0 | 1 | 0 | 0 |
| M4 | `upperWall`이 `noSlip` 대신 `fixedValue (-32.2 0 0)` | 0 | 0 | 4 | 0 | 0 |
| M5 | 아래쪽 절반의 입구 면 65개 중 32개는 속도 0, 나머지는 32.2 m/s | 0 | 0 | 8 | 0 | 8 |
| **80개 중 맞힌 수** | | **41** | **42** | **67** | **45** | **56** |

상수 기준선은 80개 중 40개입니다. 요청 문장만 보는 어떤 규칙도 40개를 맞힙니다. 문장은 프레임의 단계와
시각만 다르고, 8가지 문장이 각각 정상 프레임 5개와 잘못된 프레임 5개에 나오기 때문입니다.

- **31B와 규칙.** 프레임 15개에서 다릅니다. 31B가 13개, 규칙이 2개를 맞힙니다. M2와 M4를 빼면 31B는 64개 중
  55개, 규칙은 56개입니다.
- **M1과 M5.** 31B의 이유 16개가 모두 색 막대의 최댓값을 주어진 속도와 비교합니다. 규칙과 같은 비교입니다.
- **M4.** 변경이 표시 영역 밖에 있으므로, M4로는 모델이 변경을 알아채는지 알 수 없습니다. 31B의 답 4개는
  정상 프레임에서 낸 오경보 2개와 같은 말을 씁니다.
- **점성을 바꾼 M2**는 모델이 알아채고, 정상 실행 없이 구하는 수치로는 잡히지 않는 유일한 경우입니다. 근거는
  약합니다. 실행이 하나이고 프레임이 서로 비슷합니다.
- M2 프레임에는 와류가 없고 p가 매끄럽습니다. 이유 15개 중 13개는 실제로 있는 재순환을 없다고 하며, 점성을
  말한 이유는 없습니다.

설계 밖의 확인은 [수치의 근거](evidence/2026-10-30-wrong-setup/README.md#수치의-근거)의 기록에 기댑니다.

| 확인 | 정상 실행 필요 | 80개 중 맞힌 수 | 40개 중 오경보 |
|---|---|---:|---:|
| 실행 전체의 가장 큰 Courant 수가 1 초과, M1, M3, M5를 찾음 | 아니요 | 64 | 0 |
| 색 막대 끝 숫자 네 개 중 하나가 정상 프레임 범위 밖 | 예 | 75 | 0 |
| 같은 확인, 각 정상 실행을 나머지 네 실행의 범위와 비교 | 예 | 68 | 7 |

이유는 AI 에이전트 하나가 판정했으며, 두 번째 판정자나 사람의 확인은 없습니다. 잘못된 프레임에서 나온
`inconsistent` 이유 37개 중 14개는 변경이나 그 눈에 보이는 효과를 말하고, 17개는 부분적으로 말하며, 6개는
말하지 않습니다.
