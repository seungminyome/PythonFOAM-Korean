# 10월 30일: OpenFOAM 버전, 원본 PODFoam, 잘못된 설정 시험

MedicineBow 클러스터, 2026-10-30 · NVIDIA A30, NVIDIA L40S와 CPU 노드 · llama.cpp b11429(커밋 `d812350`) · Slurm 작업과 코드: [기록](#기록)

[README](../README.md) · 근거 자료: [버전과 원본 비교](evidence/2026-10-30-versions/README.md), [잘못된 설정 시험](evidence/2026-10-30-wrong-setup/README.md) · [영문](https://github.com/seungminyome/PythonFOAM/blob/main/docs/results-20261030.md)

관찰 기능을 넣은 PODFoam은 OpenFOAM v2012, v2106, v2212, 8에서 빌드되고 연결 검증을 통과합니다. v2012, v2106,
v2212에서 관찰 기능의 프레임은 바이트 단위까지 같습니다. OpenFOAM 8은 100단계에서 v2212와 U에서 최대 37.2 m/s 중
3.18, p에서 최대 425 m²/s² 중 23.5 다릅니다. 원인은 조사하지 않았습니다. OpenFOAM 8에서 원본 PODFoam과 비교하면 U,
p, phi는 바이트 단위까지 같습니다. POD 모드는 다릅니다. 원본에서는 각 스냅샷 구간의 첫 스냅샷을 다음 스냅샷이
덮어쓰기 때문입니다. Python에서 이 덮어쓰기를 재현하면 모든 모드가 원본과 같습니다(30개 중 30개, 150개 중 150개).
openfoam.com에서는 원본의 압력 줄을 쓰면 같은 결과가 나옵니다. 이 포크의 줄은 그 버전의 `pimpleFoam`처럼 p를 풀며,
그 차이는 2×10⁻⁶ s 뒤 U에서 최대 75.8 m/s 중 0.0508, p에서 5,142 m²/s² 중 847입니다. 실행의 설정이 잘못되었는지
물었을 때 Gemma 4 31B는 프레임 80개 중 67개를 맞혔고, 12B, 26B-A4B, Qwen3.5-35B-A3B는 41, 42, 45개를 맞혔습니다.
상수 기준선은 40개, 최대 |U| 규칙은 56개입니다. 31B의 우위를 만든 실행 두 개를 빼면 64개 중 31B는 55개, 규칙은
56개입니다.

연결 검증은 PODFoam을 직렬로 10단계 실행해 `pimpleFoam`과 비교합니다. 대상은 Python이 가진 스냅샷, 돌려준 모드, U와
p입니다([검증 README](../Solver_Examples/PODFoam/validation/README.md)). 모델 없는 관찰 기능(`LLM_ENABLED=0`)은 프레임과
텔레메트리를 쓰고 요청은 보내지 않습니다. 프레임은 한 단계의 `U.png`, `p.png`, `fields.npz`,
`readable-metadata.json`입니다. 원본은 `6fde869`의
[argonne-lcf/PythonFOAM](https://github.com/argonne-lcf/PythonFOAM)입니다. PR 트리는 브랜치 `pr/podfoam-observer`로, 원본에
이 포크의 솔버와 관찰 기능 파일을 더하고 실험 스크립트는 뺀 것입니다. 대역 서버는 고정된 답을 주며 이미지를 읽지
않습니다. 두 프레임의 차이는 셀 전체에서 가장 큰 |ΔU|와, 각 p의 평균을 뺀 뒤 가장 큰 |Δp|이며, 최대 |U|와 p의
범위에 대해 적습니다.

  스냅샷 행렬의 앞 두 열이 같습니다. OpenFOAM 8에서 제공된 케이스 실행의 행렬 6개 중 6개(SVD마다 u, v, w), 안정화한 실행의

  모두 같습니다.
- **openfoam.com의 압력.** 외부 보정이 하나이면, 그곳에서 원본의 단순한 `pEqn.solve()`는 모든 보정에서 `pFinal`을 고릅니다.

24950749와 24950748).

**PODFoam 사용자에게 달라지는 다른 점**([검증 README](../Solver_Examples/PODFoam/validation/README.md#원본-podfoam과-달라지는-점)에서):

- 모드 파일은 무차원 `zeroGradient` 필드입니다. 원본의 모드 파일은 U 성분의 복사본이며 U의 차원과 경계 조건을 가집니다.
- 부동소수점 트랩은 솔버에서 켜져 있고 Python 구간에서 꺼집니다. 그래서 원본 빌드에서 오버플로를 지나 계속되는 실행이
  여기서는 SIGFPE로 멈춥니다.
- 제공된 모듈의 `online_mode = False`는 짧은 시험의 `writeInterval` 3과 6에서 멈췄습니다. 아주 작은 음의 고유값이 `np.sqrt`에서
  NaN이 되고, 돌려준 모드는 유한해야 하기 때문입니다. 원본 빌드는 같은 케이스에서 종료 코드 0으로 끝났습니다(작업 24950748과
  24950749).
- `Py_FinalizeEx()`는 끝에서 실행되고 데몬이 아닌 스레드를 기다립니다. 그런 스레드를 시작한 모듈은 스레드를 멈추기도 해야
  합니다. 그런 스레드가 있는 시험 모듈은 여기서 제한 시간에 멈췄고, 원본 빌드는 종료 코드 0으로 끝났습니다.
- `podSvdInterval`이 0보다 크면 POD 필드만 든 시간 폴더가 생길 수 있습니다. 그 폴더가 가장 최근이면 `startFrom latestTime`은
  `p`가 없어서 멈춥니다.

## 모델이 잘못된 설정을 알아볼 수 있는가?

계단 케이스를 `pimpleFoam`으로 돌린 실행의 한 상태에서 v2 이미지 두 장을 모델 네 개에 보여 주고, 의도한 설정을 말로 알려 준
뒤, 이미지가 그 설정과 맞는지 물었습니다. 어떤 종류의 실수인지는 말하지 않습니다. 세트는 요청 80개입니다. 정상 실행 다섯
개와 항목 하나를 바꾼 실행 다섯 개에서 각각 상태 8개이고, 모든 실행은 8,000단계 뒤 정상 종료했습니다
([근거 자료](evidence/2026-10-30-wrong-setup/README.md)).

정상 프레임에 `consistent`, 잘못된 프레임에 `inconsistent`라고 답하면 맞은 것입니다. `cannot_tell`은 양쪽 모두 틀린 것이며, 이렇게
답한 모델은 없습니다. 규칙은 표시 영역의 최대 |U|가 주어진 32.2 m/s의 1배와 2배 사이이면 `consistent`라고 합니다.
